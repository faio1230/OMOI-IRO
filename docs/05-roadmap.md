# OMOI-IRO MVP開発ロードマップ

## 進め方

設計合意→実機の不確定要素の検証→Core→入出力→同期→GUI→通し試験の順で進める。ここに書いた検証アプリやCore実装は次工程であり、今回の設計作業では作成しない。

両ビューは共通タイムコード方式で同時に評価する。Sessionを後回しにしない。検証ゲートで前提が崩れた場合は、その部分の方式を修正してから依存する工程へ進む。

## フェーズ

| 段階 | 目安 | 成果物 | 完了条件 |

| P2 MIDIとLaunchpad | 3〜5人日 | midir backend、操作転送、LPX Adapter、出力mailbox | 入力と30 fps LEDの併用、復帰処理が両OSで動く |
| P3 同期とRuntime | 6〜10人日 | MTC/Clock decoder、Link Adapter、補間、stop/seek/loop、同期断 | 両ビューで同じ共通時計に追従、欠落からrelockできる |
| P4 Tauriと編集体験 | 6〜10人日 | 接続GUI、timeline、preview、preset、Undo/Redo、保存 | GUIだけでショー作成からLive追従まで実施可能 |

Linkの調査とAdapterを含め、合計27〜45人日を初期見積りとする。1人の実装担当が継続して作業し、実機試験枠を確保できる場合、調整期間込み7〜11週程度を計画上の目安にする。Macは放置運転不可のため、立ち会い試験の待ち時間はこの暦日目安に追加され得る。ブリッジの新規開発とLTC変換はこの見積りに含めない。P0後に再見積りする。

## Macの実機試験を短時間で進める方法

Apple Silicon MacとLaunchpad Xを、利用者が立ち会える時間だけ使う。各枠は15〜20分程度を案とし、確保できる時間に合わせて調整する。放置運転や常時接続を前提にしない。

| 枠 | 主な確認 | 対応タスク |
| --- | --- | --- |
| 1 | ポート識別、Programmer Mode、RGB、操作転送、終了時の復帰 | S01,S02 |
| 2 | Linkの拍・tempo・開始停止、途中参加 | S07 |
| 3 | MTC、両ビュー、seek/loop、tempo変更 | S03,S04 |
| 4 | LEDと入力の併用、同期断、USB再接続 | S05 |

準備できる設定表・操作手順・期待結果は先に用意する。各枠で時刻付きログと環境情報を保存し、解析とパーサー・状態機械の記録再生は実機を占有せずに行う。記録再生の成功をMacのUSB・driverの検証結果とはしない。

機能確認が済めば次の開発工程へ進める。2時間の連続安定性試験は別の立ち会い枠を確保して実施し、確保できるまでは未検証と記録する。短い試験を合計して2時間の連続試験に合格したとは扱わない。

## P0で検証する操作列

両OSで同じLive Setを用意する。使用版・OS build・MIDI backend・仮想バス・機器firmwareを記録し、下記をArrangementとSessionでそれぞれ実行する。

1. 起点からPlay、Stop、再開。MTCのFull Frame/Quarter FrameとLink Start Stop Syncを記録する。代替Clock方式も別に評価する。
2. 途中位置から再生、前後seek、短いloopを20回。LEDの現在位置とMTCの位置が一致するか確認する。
3. BPM 120→128→90、およびテンポ変更を伴うシーン起動。タイムコードに意図しないジャンプがないか確認する。
4. Sessionでクリップを変更し、Arrangementへ戻す。演出がclip先頭へリセットされないことを確認する。
5. 実行中のMTCブリッジ終了、Link peer喪失、Clock停止、USB抜き差し。状態表示と再接続を観測する。
6. Live再生中にアプリがLinkへ参加する。停止と誤判定せず、共通時刻をゼロへ戻さないことを確認する。

一度に1台だけLaunchpadを操作し、DAW側の実ポート自動接続がモードを戻していないかも確認する。同期テストではアプリ内の表示値だけを正解とせず、送信器のタイムコードと受信記録を比較する。

## P0後の状態（2026-10-28）

P0はWindowsで完了。LiveMTCは不採用、Linkは合格（アプリ側Start Stop Syncなし）、共通時計は自前ブリッジ方式に改訂（[10-live-bridge.md](10-live-bridge.md)）。P1以降のマイルストーンと分担は [11-implementation-plan.md](11-implementation-plan.md) に置き、この文書のフェーズ表は参考値とする。

## 採用判断

| 検証結果 | 次の対応 |
| --- | --- |
| LiveMTCが共通時計契約を満たす | 既存ブリッジを利用しP1以降へ進む |
| LinkがS07に合格 | 標準の拍入力として採用。不適合環境ではMIDI Clockを選択 |
| Sessionまたはテンポ変更で期待と異なる | 小規模M4Lブリッジの仕様を作り直し、同じ操作列で再評価 |
| 映像側がすでに安定したLive由来LTCを持つ | LTC→MTCの外部変換を比較。遅延・停止・seekを再評価 |
| 仮想バスが対象Windowsで不安定 | OS MIDI Services等の経路を評価し、MIDI backendを局所変更 |
| 30 fps全更新が不安定 | 差分・送信予算を調整。fpsを下げる必要があればPRDと合意する |

LinkまたはMIDI Clockだけで動作しても、共通タイムコード要件の完了とはしない。既存ブリッジの不適合を理由に、無断で同期方式を別の意味へ変更しない。
